# Singularity Dynasty

A subscription website for a dynasty fantasy football data-science business. Originally a single static `index.html` landing page (kept at repo root for reference); the live build is now a Next.js app in `web/`. This file is context for continuing the build in Claude Code.

## Brand
- **Name:** Singularity Dynasty
- **Theme:** space / black-hole aesthetic, with a secondary neon blue accent alongside the primary orange "event horizon" glow. A few minimalist football touches are woven in (the draft board grid mockup) but the site is not fully space-themed or fully football-themed — it's a deliberate blend.
- **Tagline / core concept:** "Where the data reaches its endpoint." The brand metaphor is gravity: scattered stats, trends, and matchups all collapse toward one clear number. The top pricing tier is literally named "Singularity" — the endpoint the whole brand points toward.
- **Voice:** confident, data-first, anti-"gut feel". Founder is a data analyst who got tired of vibes-based rankings.

## Design system
- Colors: `--void` (#07070C, near-black bg), `--void-panel`/`--void-panel-2` (card backgrounds), `--horizon`/`--horizon-gold` (orange/gold accretion-disk accent, primary), `--neon-blue`/`--neon-blue-dim` (secondary accent, deliberately present throughout — ticker, nav, node numerals, footer, not just decorative glows), `--star`/`--star-dim` (text)
- **Light mode exists** alongside the dark theme above (dark is still the default). Activated via `@media (prefers-color-scheme: light)` plus an explicit `:root[data-theme="light"]` override, toggled by the sun/moon button (`app/ThemeToggle.js`) on every page, persisted to `localStorage`. Theme-aware values that aren't plain hex (shadows, the starfield dot color, the ticker/menu-btn scrim, orbit-ring lines) are done as `--x-rgb` custom properties consumed via `rgba(var(--x-rgb), alpha)` — **never bake a theme-specific color into a static SVG data-URI**; that's what broke the feature-list bullet icons in light mode the first time (see globals.css `.feature-list li::before`, now a `radial-gradient` using `var(--void-panel)` instead).
- Fonts (changed Oct 12 2026 from Space Grotesk / Inter / IBM Plex Mono; the mono was Overpass Mono first, to look less like a template site and more hand-made): **Big Shoulders** (condensed, scoreboard / jersey-number feel; headings, the brand name, buttons, `var(--font-display)`), **Libron** (a free SIL-OFL reading serif by Nico Verbruggen, self-hosted from `web/app/fonts/` with its license; body text and labels, `var(--font-body)`; it only has Regular / Bold + italics, so CSS weights 500/600 resolve to those) and **Martian Mono** (numbers, tables, small uppercase labels, `var(--font-mono)`; chosen Oct 12 2026 over Overpass Mono -- it is wide, so its width axis is narrowed to 82% with `html{font-stretch:82%}` at the end of `globals.css` so compact panels like the percentile bars and stat tables keep labels on one line). Loaded in `web/app/layout.js` (`next/font/google` for the two Google fonts, `next/font/local` for Libron). Buttons (`.btn-primary`, `.btn-ghost`, `.round-btn`) are set in the display font, uppercase. The old `--font-space-grotesk` / `--font-inter` / `--font-ibm-plex-mono` names no longer exist.
- **Type roles (the rule that keeps a small widget from mixing fonts; block at the end of `web/app/globals.css`):** display font only for headings, the brand, nav, the three button classes and big figures (nothing smaller than ~17px except brand/nav); **Libron for prose and names** (players, teams, tooltips); **Martian Mono for everything that is data or chrome** -- numbers, chart/SVG labels, small panel titles (mono uppercase eyebrow style), stat-name labels in the stat tables, and every control (buttons, inputs, selects, toggles, filter headers). New components should pick a role, not a font; if a new control or chart label looks serif, add it to that block.

- **Live polling cadence (Oct 19 2026):** My Team's live poll (`pollLiveScores`, `MyTeamClient.js`) runs every 15s while any game is in progress (`gameStatesRef`) and every 30s otherwise; the ESPN scoreboard cache (`lib/gameStatus.js`) shrinks to 10s while a game is on. Scores can still trail the NFL by Sleeper's own refresh (it posted a first-minute scoring play a few seconds to a minute late in a check on Oct 19).
- **Live-score timing, measured Oct 19 2026 (Monday night game):** every upstream call is fast from the server (Sleeper matchups ~25ms a league, six leagues in parallel ~80ms, ESPN scoreboard ~130ms, ESPN plays ~170ms); ESPN's play list runs ~25s behind the real play. **Sleeper's own `players_points` lags the real play by about 1.5-2 minutes** (a 7-yard catch at 00:53:07Z reached Sleeper at 00:54:52Z) -- that is the main reason the Playing now scores trail the game, and it is outside our control; the Recent plays list (with each play's points) is ahead of the score column for that reason. The other cause found: the live poll skipped itself when the browser tab was hidden, and a second monitor covered by another window counts as hidden (Chrome also slows page timers to ~1 a minute after a few minutes hidden). Fixed with `lib/backgroundTimer.js` (a Web Worker keeps time) and by polling while the full-screen board is open even if the tab is hidden. `pollLiveScores` logs `[poll]` stage timings to the runtime logs.
- **Live points ahead of Sleeper (Oct 19 2026, founder: a player's number sat at 2.1 while his newest play was already in the list):** the Playing now panel adds the plays Sleeper hasn't posted yet to each player's number. `getLivePlays` also returns `totals` (each player's running standard-PPR points play by play, unrounded, from `playerPlayTotals`); `pendingFor` / `applyPending` in `lib/liveFeed.js` take a player's Sleeper number in each league he starts in, find the point in his running total it equals (within 0.02 -- Sleeper posts exact two-decimal points), and treat the later plays as pending. It only speaks when EVERY league's number lines up and agree; any mismatch (half-PPR, bonuses, a play `roleLabel` doesn't list, team defenses) means no estimate and the plain Sleeper number. Checked against live data: Daniels 3.78, McCaffrey 13.10 and Kittle 12.00 matched Sleeper to the cent; Purdy (Sleeper 2.5 higher than the plays) correctly got no estimate. A row with pending points shows just the amount ("+1.2", the same gold style as the scoring flash; the tooltip explains) in place of the projection line; it clears when Sleeper catches up. The same adjustment is applied to the open league's matchup panel on the Sunday board (`applyPendingToLineup`, `playTotals` lifted to `SundayBoard`): **every number on the Sunday board is on the same clock (founder, Oct 19)** -- `lib/adjustedMatchup.js` `adjustedMatchup(settings, gameStates, playTotals)` adds the pending points to each lineup row, the two team totals and the projected finals, and RECOMPUTES the win chance from the adjusted lineups (so the percentage always agrees with the scores; with nothing pending it hands back the server's `winChance` and Sleeper's totals untouched). It feeds the league cards (scores, word, % to win, the ring), the header caption, the board filters and the open matchup panel (`matchupState` in `SundayBoard.js`, `MatchupBody` in `MatchupPanel.js`). New play totals are MERGED into the known ones (`mergeTotals`) so opening one league, which narrows the plays request to its players, doesn't make the other leagues' cards flicker back to Sleeper's older number. Still on Sleeper's own numbers: the roster table, the standings / playoff odds, and the dashboard's matchup view outside full screen (no play-by-play there).
- **Our win chance vs Sleeper's -- OPEN, to be compared at the end of the game (founder, Oct 19 2026; he asked only to keep a note, no change to the model):** for the same matchup ("4th and Golden" vs "Olave Garden", week 6) our site said 67% to win while Sleeper said 42%. What is known: Sleeper's own weekly projections for the whole lineup match ours to within ~1 point a player (McCaffrey 20.5 vs our 20.8, Daniels 17.1 vs 17.7, Kyren Williams 20.8 vs 20.0, ...), so the gap is not the projections. Run on the real lineups, our model said 41% (Sleeper 42%) while McCaffrey was at Sleeper's earlier 18.1, and 67% once his points reached 24.2 (team 82.0 vs 96.7, one half left): `lib/winChance.js` banks the points already scored and adds the time-based rest of the game (`f x median`) for each player still playing, so McCaffrey projected to ~24.2 + 10.4 = ~34.6 and the team to 101.3 vs 97.3. **Sleeper is projecting McCaffrey to finish around 30 (founder's reading of the Sleeper app), i.e. ~5.8 more points, not the ~10.4 we add** -- so Sleeper does credit a player past his projection with remaining points, just fewer than we do; **Second data point (founder): Sleeper also projects Daniels, the only other player of mine still playing, to finish at 11.7 (he has 4.2, so ~7.5 more).** Together Sleeper expects ~13.3 more points from my two players against the ~19.3 our model adds (McCaffrey ~10.4 + Daniels ~8.9); with Sleeper's numbers my team finishes ~95.3 against the opponent's ~97.1, which is about the 42% Sleeper shows, so **the whole gap is the rest-of-game estimate**. Sleeper's remaining points are NOT a flat time share of the pregame projection (McCaffrey 5.8 = 28% of his 20.5, Daniels 7.5 = 44% of his 17.1, at the same point of the same game), so it uses its own live projection source; how it scales them is not known (an earlier note here guessed "projection minus points scored, floored at 0", which the 30 contradicts -- don't use it). **Third reading (founder's screenshot, Oct 19 ~10:25 PM ET, 0:15 left in the 3rd quarter of WAS @ SF): "4th and Golden" 91.56 vs "Olave Garden" 96.68, projected finals 101.3 vs 97.0, our site FAVORED 78% to win, Sleeper 35% for the same score -- REPRODUCED: running `matchupOutlook` on the stored lineups with my score raised to 91.56 gives 78.2% (so this is the model's honest output, not a display glitch). The model's reasoning: 25% of the game is left, my two players still on the field (McCaffrey, 27.1 pts on his 20.8 projection, and Daniels, 6.8 on 17.7) are expected to add ~9.7 (a quarter of each projection), the opponent's one player ~0.3, so a 5.1-point deficit is ~4.4 points inside the expected gain. Sleeper's 35% means it expects far less than 9.7 from those two (about 2-3 points). The gap has widened as the game went on (67% vs 42% at halftime, 78% vs 35% now): the more of the game is gone, the more our model trusts `fraction left x full-game projection` and the more Sleeper evidently discounts it.** **Sleeper's projected finals at that point (founder, 0:15 left in the 3rd): McCaffrey 28.79, Daniels 13.09.** Their points then were 27.1 and 10.84 (checked on Sleeper's feed, 4th quarter just starting), so Sleeper expected only ~1.7 + ~2.3 = **~3.9** more points from the two, against the ~9.7 our model adds (a quarter of 20.8 + 17.7); with Sleeper's numbers my team finishes at ~95.5 vs the opponent's ~96.9, which is the 35% it shows. The pattern across readings: Sleeper's projected finals barely move as the game goes on (McCaffrey 30 at halftime -> 28.79; Daniels 11.7 -> 13.09, even though those two scored +2.9 and +6.6 in between), so its rest-of-game estimate shrinks roughly one-for-one with points already scored -- it behaves like a roughly fixed projected final minus what's scored -- while ours is `time left x full-game projection` on top of whatever is scored. Sleeper's remaining for the pair: ~13.3 at halftime (50% left) and ~3.9 now (25% left) vs ours 19.3 and 9.7. (SF also led 23-10 by then, which may be part of why Sleeper trims the runner and passer; we have no game-script term.) **First outcome check (founder, Oct 19 ~10:32 PM ET): McCaffrey passed Sleeper's projected final of 28.79 on the very first play of the 4th quarter** (an 8-yard catch, +1.8, took him from 27.1 to 28.90 by the play-by-play; Sleeper's own feed hadn't posted it yet) with 15:00, a quarter of the game, still to play -- so Sleeper's projected final for him was already beaten with a full quarter left, which is the direction our larger remaining estimate (he was expected to reach ~32.3: 27.1 + a quarter of 20.8) would predict. One player, one play, not a test. Next step is to compare both numbers with the final result of this matchup (and ideally more games); until then nothing is changed. If a proper test is wanted, ESPN play-by-play for past weeks can rebuild half-time snapshots to backtest the remaining-points rule.

## Performance notes (Oct 19 2026 audit -- keep these true)
Measured on the production build: warm pages answer in 10-40ms and the data caches serve stale-while-revalidate, so the slow moments were (a) the first request on a fresh server instance, (b) signed-in page loads, which stacked network calls. Fixed:
- **Identity on read paths is a local JWT check, not a network call:** `lib/authUser.js` `getAuthUser()` (Supabase `getClaims()`, this project signs tokens with asymmetric ES256 keys so verification needs no round trip) is used by `proxy.js` (every navigation), `SiteHeader`, the landing page, `lib/tier.js` `resolveTier` and the read-only My Team actions (`refreshSavedTeams`, `pollLiveScores` -- every 30s --, `getLivePlays`, `getRosterNews`). A signed-in page load used to call Supabase Auth's `getUser()` 3-4 times in a row. **Anything that changes data or money (saveTeam, deleteTeam, setBuyIn, quiz, checkout, billing, account) keeps `getUser()`.** The proxy matcher also skips `api/webhooks` and font files.
- **Sleeper's 16MB player dictionary is no longer in the critical path of the tool pages:** `getPlayerBiosByNamePos()` (awaited by Weekly Rankings, Player Sims and both compare pages) is cached for a day in Next's shared data cache (~1MB entry, under the 2MB limit) instead of only in each server instance's memory, so a fresh instance doesn't download + parse it before answering. A failed download is never cached as "no players". (My Team's own use, `getSleeperPlayers()`, still caches per instance and is capped at 3s on the page.)
- **My Team no longer loads what it doesn't show:** the Analytics tab's game log (~215KB of JSON in the HTML for 6 leagues) loads on demand when that tab opens (`getMyGameLogs` -> `lib/myGameLogs.js`, parallel pages); the season-sim numbers are cached 5 minutes (`getCachedPlayerSims`); and the portfolio summary is computed in memory instead of being written to the database on every page view (nothing read the stored copy).
- **Paged reads run in parallel (`lib/fetchAllRows.js`):** the first page also returns the exact row count and the remaining 1000-row pages are fetched together instead of one after another (the 8,105-row game log: 1.9s -> 0.5s, identical rows; every cold cache on the site uses it).
- **The badge inputs read EVERY game (Oct 19 2026, founder):** `fetchAchievementInputs` / `fetchHistoricalFloorCeiling` in `app/tools/achievementsData.js` used plain selects, which Supabase caps at 1000 rows -- the game log read stopped at the newest ~four weeks (weeks 3-6 of 6), so Super Hero wins missed the earlier weeks (the ticker and My Team badges; Gibbs showed 1 win instead of 4, 30 players were off) and the per-game floor / ceiling join behind On Fire / On Thin Ice came from an arbitrary 1000 of ~2,700 published rows. Both now page through everything with `fetchAllRows` (stable orderings), and the result is kept 5 minutes per server instance because My Team's refresh runs it on every page view. **Any read of a table that can pass 1000 rows must use `fetchAllRows`.** (The Weekly Rankings page had its own paged copy and was already right.)
- Ticker inputs (`SiteHeader`'s whole-game-log computation, the heaviest cached read) revalidate every 10 minutes instead of every 60 seconds; the data only changes when a week is published.
- **Still open / recommendations:** the first visitor after each deploy still pays ~1.3s (cold data caches); Libron's two italic files (~176KB, preloaded on every page) are effectively unused -- dropping them is a font change, so it needs the founder's OK; Weekly Rankings renders every row for Explorer+ (hundreds of inline SVG curves) which is heavy to hydrate -- paging or virtualising the table is the next big client-side win.
